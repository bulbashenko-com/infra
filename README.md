# infra

Single source of truth for the bulbashenko.com platform. If it runs, it is described here.

| Layer | Tool | Path |
|---|---|---|
| Servers, firewalls, network, IPs, DNS, Tunnel | OpenTofu (hcloud, cloudflare) | `terraform/` |
| Cluster bootstrap and reconciliation | Flux (branch `main`; staging from `dev`) | `clusters/hel1/` |
| Platform (ingress, certs, tunnel, DB operator, monitoring, backups) | Flux + Helm | `infrastructure/` |
| Applications | Flux + Kustomize | `apps/{base,staging,production}/` |
| Secrets | SOPS + age | `*.sops.yaml` next to what uses them |

## Rules

**How development, staging and releases work — start here: [docs/workflow.md](docs/workflow.md)** (in Russian).

- Two branches. `dev` (the default branch) is **staging**: every change lands there through a pull request (CI
  green; agents may auto-merge). `main` is **production**: Flux syncs `clusters/hel1` from it. A release is one pull
  request `dev -> main`, kept open and described by a bot; the owner merges it. Every push to `main` gets a tag
  `vYYYY.MM.DD[.N]` and a GitHub Release. See [Releases](#releases).
- Secrets are committed **only** encrypted, in `*.sops.yaml`. CI rejects plaintext `kind: Secret` and unencrypted `*.sops.*` files; gitleaks scans every push.
- App versions: a push to an app repo's `main` (site, auth, mail) pins that commit on this repo's `dev`
  (image tag or Flux `GitRepository` commit), straight away and without a PR; production gets it with the release.
  By hand: `just promote <app> [sha]` (preview: `just promote-dry`).
- Rollback: `just rollback <tag>` (or Actions → rollback) opens a PR that restores `main` to that release.

## Recovery from zero

1. This repo.
2. The age private key (offline copy with the owner).
3. Data backups on the Hetzner Storage Box (rclone crypt, `box:hel1`): CNPG base backups + WAL (60 days),
   Garage buckets, Headscale and Nextcloud volume archives. Rehearsed with `apps/production/drill`.

`tofu apply` → servers come up with k3s via cloud-init → `flux bootstrap` → Flux restores everything else → restore data.

## Layout

```
terraform/           OpenTofu, state committed encrypted

infrastructure/      cluster-wide components
apps/base/           app manifests
apps/staging/        staging (bulbashenko.dev, own Ory, *_staging DBs, e2e), read from dev

```

Daily commands: `just --list`.

## Labels

Every namespace and every object we manage carries two labels (staging a third), so "mine" and "the machinery" are easy to tell apart (Headlamp, k9s, `kubectl get -l`).

| Label | Values |
|---|---|
| `bulbashenko.com/layer` | `app`: our services (site, auth, data). `platform`: what we install for them (tunnel, certs, Postgres operator, ingress, GitOps UI, access). `system`: Kubernetes/k3s internals, not touched. |
| `bulbashenko.com/app` | `site`, `auth`, `data`, `tunnel`, `certs`, `postgres-operator`, `ingress`, `gitops`, `access`, `monitoring`, `controllers`, `configs`, `kubernetes` |
| `bulbashenko.com/env` | `staging` on everything in `apps/staging` (namespaces `*-staging`); production objects have no `env` label. |

Where they come from: Namespace manifests (explicit), `labels:` in each directory's `kustomization.yaml` (`includeSelectors: false`; pod templates included for apps), Flux `commonMetadata` for the auth repo, and `infrastructure/configs/system-namespaces.yaml` for namespaces Kubernetes or Flux create themselves (prune disabled).

Examples: `kubectl get pods -A -l bulbashenko.com/layer=app`, in k9s `:pods` then `/-l bulbashenko.com/layer=app`.
kube-state-metrics exports both labels (`label_bulbashenko_com_layer`, `label_bulbashenko_com_app` on `kube_namespace_labels`
and `kube_pod_labels`) for dashboards and queries.

## Monitoring

Where to look and what each notification means: [docs/workflow.md](docs/workflow.md) ("Где смотреть", "Уведомления").

victoria-metrics-k8s-stack in `monitoring`: the operator (`infrastructure/controllers/victoria-metrics-operator.yaml`, brings
the CRDs) and the stack (`infrastructure/configs/monitoring/`: VMSingle with 30 days retention, vmagent, vmalert,
Alertmanager, node-exporter, kube-state-metrics, Grafana). Logs: VictoriaLogs plus vlagent on every node and an
event exporter (`infrastructure/configs/logging/`, 14 days).

- Grafana: https://grafana.int.bulbashenko.com (mesh only, sign-in through Ory client `grafana`; only `infra-admins` get in,
  as Grafana server admins). No PVC: dashboards and datasources come from git, upstream dashboards and alert rules from the
  chart's sync Job. Break-glass: `/login?disableAutoLogin` with the local admin from the Secret `grafana`.
- Our dashboards (folder "bulbashenko"): Здоровье (home), Релизы, Выкатка, Логи. Generated by `scripts/dashboards`
  (`python3 -m scripts.dashboards infrastructure/configs/monitoring/dashboards`); never edit the JSON, CI compares it.
  Every panel needs a description. Upstream dashboards are in the folder "Подробно".
- Datasources: VictoriaMetrics, VictoriaLogs, GitHub (read-only GitHub App `bulbashenko-com-grafana`, credentials in the
  Secret `grafana`: `github-app-id`, `github-app-installation-id`, `github-app-private-key`).
- Scrape targets: platform components in `infrastructure/configs/monitoring/scrapes.yaml`; app targets next to the app
  (`apps/production/data/scrapes.yaml`, `apps/mail/scrape.yaml`, `apps/production/nextcloud/scrapes.yaml`).
- Alerts: upstream rules plus ours in `infrastructure/configs/monitoring/rules.yaml`; Flux failures as events
  (`flux-alerts.yaml`). Everything goes to one Telegram chat (Alertmanager config in `stack.yaml`; bot set up once with
  `just telegram <token> <chat_id>`).

## Releases

The process, timings, staging, rollback and hotfixes are in [docs/workflow.md](docs/workflow.md); this is the wiring.

| App | Gate before the pin | Pin (all moved together by `scripts/promote.sh`) |
|---|---|---|
| site | `test` (check, build) green, then images `site`, `site-migrate`, `site-e2e` | `apps/base/site/kustomization.yaml`, `apps/staging/site/kustomization.yaml`, `apps/staging/site-e2e/flux.yaml` |
| auth | `test` (UI + e2e) green, then images `auth-ui`, `auth-e2e` | `clusters/hel1/auth.yaml`, `apps/staging/auth/flux.yaml` |
| mail | `CI` green | `clusters/hel1/mail.yaml` |

- Gate: Flux posts `staging/auth-e2e` and `staging/site-e2e` on the tested `dev` commit (`apps/staging-platform/notify.yaml`),
  required on `main`; `staging-gate.yml` marks them for hotfix PRs. `prod/<kustomization>` on `main` commits shows the rollout.
- `release.yml` + `scripts/release-pr.sh`: the release PR (and back-merges of hotfixes). `release-gate.yml`: "ready"
  message, auto-merge of security-only releases. `release-tag.yml`: tag, Release, rollout watch. `rollback.yml`.
- `terraform/` is applied by CI, not Flux (`.github/workflows/tofu.yml`): every PR touching it gets a plan comment,
  the release applies it. See `terraform/README.md`.
- Credentials: GitHub App `bulbashenko-com-deploy` (Contents, Pull requests, Commit statuses: write), allowed to bypass
  the `dev` ruleset (it pushes the pins). Org variable `DEPLOY_APP_CLIENT_ID`, org secret `DEPLOY_APP_PRIVATE_KEY`; Flux
  uses its own key (`apps/staging-platform/github-app.sops.yaml`). Telegram: org secret `TELEGRAM_BOT_TOKEN`, variable
  `TELEGRAM_CHAT_ID`. An App token (not `GITHUB_TOKEN`) is required so its PRs run the required checks.
- Add an app: a `case` line in `scripts/promote.sh`, the choice in `promote.yml`, and a `request-promote.yml` job in its repo.
