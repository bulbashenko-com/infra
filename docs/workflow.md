# Как устроены разработка, staging и релизы

Один документ для всех репозиториев организации (site, auth, mail, teamspeak, infra). README приложений ссылаются
сюда. Если что-то здесь расходится с тем, как работает на самом деле, неправ документ: исправь его тем же PR.

## Коротко

- **Ты делаешь одно:** мержишь PR «Release» в infra (`dev` → `main`). Всё остальное делают CI и боты.
- **staging** — копия сайта и входа на `bulbashenko.dev` (только через mesh). Туда сразу попадает всё, что смержено.
- **Прод** получает изменения только с релизом. Каждый релиз — тег `vГГГГ.ММ.ДД` и страница в GitHub Releases.
- **Видно всё в Grafana** (https://grafana.int.bulbashenko.com) и в Telegram. Flux UI и Headlamp — только для отладки.

## Модель в одной картинке

```
приложение (site, auth, mail, teamspeak)        infra
────────────────────────────────────────        ─────────────────────────────────────────────
PR ─ проверки ─ merge в main ─ образ :<sha> ─►  бот коммитит «пин» в dev ─► staging (минута)
                                                 PR в dev (конфиг кластера) ─┘      │
                                                                           e2e на staging
                                                                                    │
                                       бот держит PR «Release» dev → main ◄─────────┘
                                       ты мержишь ─► main ─► Flux ─► прод (2–5 минут)
```

Термины:

| Слово | Что это |
|---|---|
| **Flux** | Программа внутри кластера. Раз в минуту читает git и приводит кластер к тому, что там написано. Руками в кластере ничего не меняют. |
| **Kustomization** (Flux) | Кусок кластера, который Flux применяет целиком: `site`, `auth`, `infrastructure`, `nextcloud`… Это единица выкатки: у каждой своё состояние «применено / идёт / ошибка». |
| **Пин** | Строка в infra, говорящая, какой коммит приложения запускать (`newTag: <sha>` или `commit: <sha>`). Выкатка новой версии = смена пина. |
| **dev / main** | Ветки infra. `dev` — staging (и ветка по умолчанию), `main` — прод. |
| **Релиз** | Merge PR «Release» (`dev` → `main`). |

## Что происходит после merge в приложении

| Шаг | site | auth | mail, teamspeak |
|---|---|---|---|
| Проверки PR (обязательные) | ~3 мин: lint, типы, миграции, сборка | ~13 мин: UI + весь стек end-to-end | ~1 мин: манифесты |
| Merge → образы в GHCR | ~4 мин | ~5 мин | — |
| Пин в `dev` | < 1 мин | < 1 мин | < 1 мин |
| Staging обновился | 1–2 мин (с миграцией БД) | ~2 мин | нет staging |
| e2e на staging | ~3 мин | ~12 мин | — |
| **Итого до «релиз готов»** | **≈ 10 мин** | **≈ 20 мин** | ≈ 2 мин |

Пины `mail` и `teamspeak` лежат в `dev`, но работают только в проде, после релиза.

## Staging

- Адреса: https://bulbashenko.dev (сайт и админка), https://auth.bulbashenko.dev (вход), https://mailpit.int.bulbashenko.dev
  (почта, которую шлёт staging). Только через Headscale: публичного DNS у `bulbashenko.dev` нет.
- Данные: каждую ночь (03:15 UTC) staging получает контент прода (база сайта и картинки) и сразу мигрирует его до своей
  версии. Изменения в админке staging живут до следующей ночи. Обновить сейчас: `just staging-refresh`.
- Вход: свой Ory со своими аккаунтами, отдельный от прода.
- Копии в staging есть только у сайта и входа. Почта, TeamSpeak, Nextcloud, Headscale и всё в `infrastructure/`
  впервые применяются в проде с релизом; release PR предупреждает об этом, а CI показывает дифф отрисованных манифестов
  (комментарий «Что изменится в кластере»).

### e2e на staging — гейт релиза

Для каждой версии в staging запускаются тесты, их результат Flux ставит статусом на коммит `dev`:

- `staging/auth-e2e` — весь вход: пароль, TOTP, passkey, восстановление, OIDC, forward-auth, админка (тесты в репо auth, `e2e/`).
- `staging/site-e2e` — сайт: главная, 404, языки, вход админа через SSO и отказ не-админу, картинки (репо site, `e2e/`).

Оба обязательны, чтобы смержить релиз. Упал тест — в Telegram придёт ошибка, а лог есть в Grafana → «Логи»,
namespace `auth-staging`.

## Релиз

1. Бот держит открытым PR «Release: N изменений с <дата>». В нём:
   - приложения и изменения, которые войдут;
   - предупреждение о том, что не проверялось в staging;
   - комментарий «Что изменится в кластере»;
   - план OpenTofu, если менялся `terraform/`.
2. Когда staging проверен и все проверки зелёные, в Telegram приходит «📦 Релиз готов к merge».
3. Merge (только merge commit). Дальше:
   - тег `vГГГГ.ММ.ДД` и страница в Releases, в Telegram «🚀 выкатывается»;
   - Flux забирает `main` за минуту и применяет. На merge-коммите появляются галочки `prod/<часть>`;
   - через 2–5 минут (Nextcloud до 25) в Telegram «✅ применён за N мин» или «🔴 ошибка». Итог дописывается в Release.
4. Следить вживую: Grafana → **Выкатка**.

### Security-релизы

Если в релизе нет ничего, кроме обновлений безопасности (Renovate помечает их меткой `security`), PR получает метку
`security-only` и мержится сам, как только staging и проверки зелёные. В Telegram приходит «🛡 смержен
автоматически». Если в релизе есть что-то ещё, есть непроверенные в staging части или изменения OpenTofu, релиз ждёт тебя.

## Откат

Сломалось после релиза:

1. GitHub → infra → Actions → **rollback** → Run workflow → тег последнего хорошего релиза (список в Releases или в
   Grafana → «Релизы»). Или `just rollback v2026.11.14`.
2. Бот откроет PR «Rollback to v…», который возвращает `main` ровно к состоянию тега. Merge = откат, применится за
   2–5 минут, получит свой тег.
3. Откат автоматически придёт и в `dev` (staging тоже откатится). Чтобы вернуть изменения позже: revert коммита отката
   в `dev`, исправление, новый релиз.

Миграции базы не откатываются. Поэтому их пишут совместимыми с предыдущей версией: сначала добавить колонку,
следующим релизом начать использовать, ещё позже удалить старое.

## Hotfix

Когда ждать staging нельзя: PR прямо в `main` (ты мержишь). Проверки `staging/*` для него засчитываются автоматически,
релиз получает тег. Бот сам вернёт изменение в `dev` (PR «Back-merge»).

## Схема базы сайта

Изменение `prisma/schema.prisma` всегда идёт с файлом миграции (`npx prisma migrate dev --name …`); CI проверяет, что
они совпадают. Миграции применяются автоматически перед стартом новой версии (init-контейнер `migrate`): на staging сразу, в
проде с релизом. Если миграция падает, старая версия продолжает работать, а в Telegram приходит ошибка. Подробнее:
site `docs/deployment.md`.

## Обновления зависимостей (Renovate)

Политика одна для всех репо: `renovate-preset.json` в infra.

| Что | Как |
|---|---|
| Уязвимость (метка `security`) | отдельный PR, мержится сам при зелёном CI; релиз только из таких мержится сам |
| patch / minor | один общий PR, мержится сам при зелёном CI → staging → прод с релизом |
| major | один PR на репо со всеми major, обновляется на месте; мержишь сам, когда удобно |
| Stalwart, TeamSpeak, Nextcloud, Postgres, Garage, Headscale | никогда сами: мигрируют данные и не имеют staging |

Что ждёт и почему — issue «Dependency Dashboard» в каждом репо.

## Где смотреть

| Вопрос | Где |
|---|---|
| Всё ли в порядке сейчас? | Grafana → **Здоровье** (главная страница) |
| Что в проде, что на staging, что ждёт релиза? | Grafana → **Релизы** |
| Что меняется прямо сейчас, долго ли ещё? | Grafana → **Выкатка** |
| Почему сломалось? | Grafana → **Логи** (namespace = приложение) |
| Что вошло в релиз, сколько длилась выкатка? | GitHub → infra → Releases |
| Детали по узлам, подам, Kubernetes | Grafana → папка «Подробно» |
| Отладка Flux по объектам | https://flux.int.bulbashenko.com, Headlamp |

У каждой панели в Grafana есть значок ⓘ: что она показывает и когда волноваться.

## Уведомления (Telegram)

Один чат, два отправителя: Alertmanager (из кластера) и GitHub Actions (релизы).

| Сообщение | Что значит | Что делать |
|---|---|---|
| 📦 Релиз готов к merge | staging проверен, всё зелёное | смержить, когда удобно |
| 🚀 Релиз vX выкатывается | merge прошёл, Flux применяет | ничего, ждать итог |
| ✅ Релиз vX применён за N мин | всё в проде и здорово | ничего |
| 🔴 Релиз vX: ошибка выкатки | часть не применилась или не поднялась | «Выкатка» → «Логи»; если прод сломан — откат |
| 🛡 Security-релиз смержен автоматически | вышли только обновления безопасности | ничего |
| ⏪ PR отката готов | кто-то запустил rollback | смержить = откатить |
| 🔴 Flux: Kustomization X не применился / не поднялся | изменение из git не применилось; в сообщении текст ошибки Flux | «Выкатка», «Логи» |
| 🔴 / 🟡 другие алерты | авария (сделать сейчас) / предупреждение (сегодня) | описание в сообщении; ссылки на дашборды внизу |
| ✅ … — снова в норме | алерт прошёл сам | ничего |

Обязательные проверки GitHub (кто без чего не смержится) включаются один раз: `just rulesets` (после первого релиза — ещё раз, чтобы стали обязательными `staging/*`).

Бот и чат настраиваются один раз: `just telegram <token> <chat_id>` (токен от @BotFather, chat id группы, куда добавлен
бот: `curl -s https://api.telegram.org/bot<TOKEN>/getUpdates | jq '.result[].message.chat.id'`).

## Кто что может

| Действие | Кто |
|---|---|
| Merge в `main` приложений и в `dev` infra | агенты и боты, когда CI зелёный (это staging) |
| Пин версии приложения в `dev` | только deploy-бот (GitHub App `bulbashenko-com-deploy`) |
| Merge release PR в `main` infra | владелец; security-only — бот |
| Merge PR отката / hotfix | владелец |
| `tofu apply` | CI после релиза |

## Как это реализовано (для правок)

| Что | Где |
|---|---|
| Пин в `dev` | `.github/workflows/promote.yml`, `scripts/promote.sh` |
| PR «Release», back-merge hotfix | `.github/workflows/release.yml`, `scripts/release-pr.sh` |
| «Готов к merge», security auto-merge | `.github/workflows/release-gate.yml` |
| Тег, Release, ожидание выкатки | `.github/workflows/release-tag.yml`, `scripts/release-watch.sh` |
| Откат | `.github/workflows/rollback.yml` |
| Статусы `staging/*`, `prod/*` | Flux Provider `github`, `apps/staging-platform/notify.yaml` |
| Ошибки Flux → Telegram | `infrastructure/configs/monitoring/flux-alerts.yaml` |
| Alertmanager, шаблон Telegram | `infrastructure/configs/monitoring/stack.yaml` (`alertmanager`) |
| Дашборды | `scripts/dashboards/` (генерирует JSON; руками JSON не править) |
| Логи | `infrastructure/configs/logging/` |
| Проверки CI infra | `.github/workflows/ci.yml` |
